Дата обновления: 2026-10-18.

## 1. Как работать с пользователем

- Общаться по-русски, простым языком, пошагово. Не угадывать намерения и не преувеличивать степень готовности.
- Делать небольшие, проверяемые этапы. После каждого этапа останавливаться и ждать явного указания пользователя.
- **Не менять код и не запускать сборки или GitHub Actions без прямой команды пользователя.** Не создавать Pull Request без отдельного разрешения.
- Не добавлять новые зависимости. Нужны Kotlin и уже имеющиеся Android API/зависимости; **не использовать OpenCV, ML и тяжёлые библиотеки**.
- Не смешивать эту работу с проектом REDMOND SkyBalance, русским переводом или исправлением тёмной темы.
- Перед правками читать актуальный файл из GitHub, затем после записи перепроверять результат.

## 4. Тестовая база, которую готовит пользователь

Пользователь подготовил две таблицы — `192ind-tt1.jpg` и `192ind-tt2.jpg`.
- Каждая таблица: 3000 × 2000 пикселей.
- 12 столбцов × 16 строк = 192 ячейки.
- Одна ячейка: 250 × 125 пикселей.
- Две таблицы — всего 384 тестовых примера.
- Координаты задаются относительно левого верхнего угла таблицы. Для столбца `c` и строки `r`, нумерация с 1: `x = (c - 1) × 250`, `y = (r - 1) × 125`; размер ячейки — 250 × 125.
- К каждой ячейке пользователь добавит файл комментариев с координатами, шаблоном индикатора и ожидаемым значением для проверки распознавания.

В набор намеренно входят: фотографии разного качества и с разным наклоном; разные формы индикаторов; неисправные сегменты; системные сообщения и сообщения об ошибках; индикаторы, у которых нижняя часть цифр скрыта за нижней кромкой рамки. Не распознавать ошибочное/служебное сообщение как вес. Если оставшиеся сегменты дают однозначную цифру, скрытый нижний горизонтальный сегмент не должен мешать распознаванию.

**Текущий этап:** пользователь завершает алгоритм и разметку таблиц. Не начинать реализацию или тестовые прогоны до его прямого указания и готовности необходимых материалов.

План после разрешения пользователя: реализовывать по спецификации небольшими шагами и прогонять размеченные тестовые наборы. При ошибках показывать диагностическое изображение с найденными границами сегментов и их осями, чтобы пользователь мог визуально проверить, на каком этапе возникла ошибка. Не считать правильность подтверждённой, пока не пройдены эталонные тесты.

## 5. Утверждённое правило проведения осевых линий сегментов

Это важная и утверждённая пользователем геометрическая основа для сегментов любой формы и с любыми торцами.

1. На каждом сегменте найти две длинные боковые грани; при оценке не учитывать торцевые фаски, скосы, заострения и форму окончаний.
2. Оценить направление длинных граней и проверить их приблизительную параллельность.
3. Провести ось посередине между длинными гранями — на одинаковом перпендикулярном расстоянии от обеих.
4. Убедиться, что ось параллельна длинным граням. Не выводить ось из вершин, формы торцов или центра ограничивающего прямоугольника.
5. Сопоставить направление с аналогичными сегментами противоположной стороны цифры и другими цифрами группы. При расхождениях перепроверить найденные границы и согласовать ориентацию осей, по возможности сохраняя одинаковое расстояние до двух боковых граней каждого сегмента. Не подгонять ось по вершинам в ущерб этому условию.

Оси не обязаны быть вертикальными/горизонтальными относительно фотографии. Сегменты одной группы могут быть наклонены; геометрию восстанавливать по их фактическим осям.

## 6. Матрица распознавания семисегментных цифр

Обозначения:
- `+` — сегмент должен быть виден.
- `-` — сегмент не должен быть виден.
- `+ (-)` — сегмент обычно виден, но допускается его отсутствие из-за неисправности или того, что он скрыт на фото.

Порядок столбцов: верхний горизонтальный HU, средний горизонтальный HM, нижний горизонтальный HD, левый верхний вертикальный VUL, правый верхний VUR, левый нижний VDL, правый нижний VDR.

| Цифра | HU | HM | HD | VUL | VUR | VDL | VDR | Редкий вариант начертания |
|---:|:---:|:---:|:---:|:---:|:---:|:---:|:---:|---|
| 0 | + (-) | - | + (-) | + (-) | + | + | + (-) | — |
| 1 | - | - | - | - | + (-) | - | + (-) | — |
| 2 | + (-) | + (-) | + (-) | - | + (-) | + | - | — |
| 3 | + (-) | + (-) | + (-) | - | + | - | + | — |
| 4 | - | + (-) | - | + (-) | + (-) | - | + (-) | — |
| 5 | + (-) | + (-) | + (-) | + | - | - | + (-) | — |
| 6 | + (-) | + | + (-) | + (-) | - | + | + (-) | В редких случаях HU выключен |
| 7 | + | - | - | - | + (-) | - | + (-) | В редких случаях VUL включён |
| 8 | + (-) | + | + (-) | + (-) | + | + | + (-) | — |
| 9 | + (-) | + | + (-) | + | + | - | + (-) | В редких случаях HD выключен |

Редкие варианты 6, 7, 9 — альтернативные варианты начертания, отмеченные пользователем, а не разрешение игнорировать любые сегменты.

### Правило одного отсутствующего сегмента на ячейку

- В одной ячейке цифры может отсутствовать не более одного сегмента, который отмечен `+ (-)`.
- Соседние цифры проверяются независимо. В каждой ячейке может отсутствовать свой допустимый сегмент.
- Если сегмент обозначен только `+`, его отсутствие нельзя объявлять допустимой неисправностью по этому правилу: наблюдаемая комбинация может соответствовать другой цифре или быть неоднозначной.
- Нижний горизонтальный сегмент не является отдельным исключением. Он обрабатывается по той же матрице. Его можно не видеть у нескольких или у всех цифр, если для каждой ячейки соблюдается лимит одного отсутствующего допустимого сегмента и остальные признаки позволяют распознать цифру.
- Уверенное распознавание должно опираться на всю комбинацию сегментов, а не на один штрих. Если комбинация подходит нескольким цифрам, не объявлять одну из них достоверной без дополнительного основания.

Дополнительное наблюдение пользователя: ведущие нули на весах обычно не отображаются; ноль перед десятичной точкой может отображаться. Поэтому рисунок вроде `06.5`, если 0 стоит в подавленной ведущей позиции слева, может однозначно указывать на 8 с погасшим средним сегментом — фактическое показание `86.5`. Ноль непосредственно перед десятичной точкой (например, `0.65`) — нормальный допустимый ноль.

История веса может быть подсказкой в строго ограниченных неоднозначных ситуациях, например при внешне похожих 3 и 5, когда очевидна неисправность сегмента. Не использовать предыдущий вес для безусловной подмены распознанной цифры. Особенно не выводить автоматически 8 или 9 из прошлого измерения: пользователь может перейти через десяток, и это нормально. История не должна превращать догадку в достоверный факт.

## 7. Быстрый поиск первичных кандидатов

Искать сначала дешёвые признаки и только потом подробно проверять геометрию.

### Структура кандидата
- Учитывать выбранный шаблон и, если доступно, последнее успешно подтверждённое значение веса как подсказку ожидаемого числа отображаемых цифр. История — не жёсткое ограничение: вес может измениться, а ведущие позиции слева могут быть пустыми.
- Искать вытянутые сегментоподобные штрихи и объединять близкие приблизительно параллельные элементы. Максимальный промежуток первичного объединения соотносить с оценённой высотой полной цифры; межцифровые зазоры могут различаться.
- Проверять достаточное число правых вертикальных сегментов для ожидаемого числа отображаемых цифр и искать левые вертикали там, где они должны быть по рисунку цифры. Помнить, что 1 может не иметь левых или горизонтальных сегментов.
- Группа, не прошедшая первичную проверку, отбрасывается; поиск продолжается. Ложная группа не должна завершать распознавание всей фотографии.

### Последовательность углов
1. Сначала строго вертикальные оси — 0°.
2. Затем небольшой наклон вправо.
3. Затем такой же небольшой наклон влево.
4. Если результат не найден, постепенно увеличивать угол и чередовать вправо/влево, пока не найдён кандидат или не достигнут предел ±45°.
5. При каждом угле проверить все подходящие группы прежде, чем расширять угол. Если группа не проходит проверку, проверить следующую при том же угле.

Начальный угол и шаг изменения — параметры реализации, которые надо подобрать по размеченным фотографиям. Не запускать дорогой исчерпывающий поиск по всем углам и всем пикселям сразу.

## 8. Шаблоны и приоритеты распознавания

Функциональная спецификация содержит актуальный порядок. Важнейшие правила:

- Добавить шаблон **«Неизвестен»** и сделать его выбором по умолчанию. Он означает, что пользователь не определял тип индикатора или не знает, что выбрать.
- Если в настройке «Неизвестен»: сначала использовать сохранённый технический профиль индикатора; если профиля нет или он не помог — автоматическое определение формата и геометрии.
- Если пользователь явно выбрал шаблон: сначала попытка по выбранному шаблону; при неудаче — сохранённый технический профиль; затем автоопределение.
- Автоматически выявленный формат не меняет настройку пользователя с «Неизвестен» на конкретный шаблон. После успешного распознавания, подтверждённого пользователем, установленный формат/правило поведения сохраняется в техническом профиле.
- Для индикаторов с плавающей десятичной точкой нужно сохранять правило, как число знаков меняется в зависимости от величины веса, а не просто текущий формат (пример: ниже 100 — `XX.XX`, от 100 — `XXX.X`).
- Точку не обязательно обнаруживать как отдельный объект, если её положение надёжно следует из шаблона/структуры. Фотографии показывают, что точка может быть плохо различима.

Поддерживаемые варианты, встречающиеся в спецификациях: `XXX.XX`, `XXX.X`, `XXX.Xx`, `XXX.xx`, `XXX.XXX`, `XXX.`, `XXX.XX xx°C`. Шаблон «Мультидисплей» предназначен для многофункциональных ЖК-экранов, где несколько показаний располагаются в разных рядах или группах. Редкий формат `XX.X.Xxxx` содержит справа три малые цифры уровня заряда; эти цифры не записывать в базу openScale как измерение заряда.

В текущем функциональном документе есть старый специальный пункт для редкого индикатора, где два варианта десятичной точки предлагается разрешать через возраст профиля. Это может расходиться с общим принципом не использовать возраст для распознавания; при возвращении к этому особому индикатору нужно согласовать/устранить противоречие, а не незаметно использовать возраст для обычных распознаваний.

## 9. Системный технический профиль

- Хранить в существующем Android DataStore Preferences, без новых таблиц Room, миграций и изменения схемы базы.
- Профиль общий для приложения на устройстве, не привязывается к ID пользователя openScale. Не вводить управление множеством профилей на первом этапе.
- Может включать цвет сегментов/фона и допуски, геометрию, HC/VC, привычную ориентацию и удачный угол поворота, определённый шаблон или правило плавающей точки.
- В режиме «Мультидисплей» дополнительно хранить координаты области веса относительно границ выправленного ЖК-экрана.
- Сохранять и обновлять параметры только после успешного распознавания, подтверждённого пользователем. Неудачный/неподтверждённый результат не должен портить профиль.
- Настройки DataStore и технический профиль не входят в резервные копии базы данных; существующий механизм бэкапа не менять. После установки на другом устройстве параметры определяются заново.
- Сохранение фото дисплея — отдельная добровольная настройка, выключенная по умолчанию. Профиль должен работать без архива фотографий.

## 10. Фотографии, повороты и повторные попытки

При каждом снимке применяется один и тот же приоритет шаблона, затем проверяются ориентации. Если есть ранее найденный удачный угол поворота, его использовать в числе первых попыток; затем проверить два других предусмотренных варианта. Для каждой ориентации повторять весь применимый порядок: неизвестный шаблон — профиль → автоопределение; явный шаблон — выбранный шаблон → профиль → автоопределение.

**Первая фотография:** все способы на исходной ориентации и предусмотренных поворотах. Если неудачно, попросить более качественный снимок. Не показывать рамку области веса на первой неудаче.

**Вторая фотография:** повторить тот же цикл. Если неудачно:
- попытаться обнаружить границы ЖК-экрана;
- если удалось — выправить экран по найденным границам, исправляя наклон/перспективу, и показать рамку, которую пользователь совмещает с областью веса;
- если границы найти нельзя — показать рамку в центре фотографии и попросить натянуть её на цифры веса.
После ручного выбора повторить распознавание внутри рамки. После успешного распознавания пользователь подтверждает результат; только тогда сохранять профиль/относительные координаты области.

**Третья фотография:** при необходимости повторить цикл и использовать сохранённую область веса после повторного обнаружения/выправления экрана. Если все предусмотренные попытки с третьей фотографией неудачны, сообщить, что дисплей не удалось распознать текущим алгоритмом (возможен неподдерживаемый тип индикатора, например стрелочный или газоразрядный).

Явный выбор шаблона «Мультидисплей» остаётся отдельным режимом: для первого использования области веса пользователь указывает её заранее после обнаружения и выправления границ ЖК-экрана. При последующих снимках рамка восстанавливается по относительным координатам.

## 11. Обработка результата и сохранение

- Использовать штатные механизмы openScale `MeasurementFacade` и `UserFacade`.
- Подтверждение результата обязательно. Сомнительный результат не должен сохраняться автоматически.
- Время измерения — время съёмки фотографии, не время распознавания или подтверждения.
- Новое распознанное показание создаёт новую запись взвешивания.
- Температуру, если она предусмотрена шаблоном и настройка включена, сохранять строкой в стандартном комментарии; отдельную таблицу/тип измерения температуры не вводить.
- При включённой пользователем опции сохранения фотографии прикреплять штатное обрезанное фото дисплея к подтверждённой записи; без включения опции постоянный архив снимков не создавать.
